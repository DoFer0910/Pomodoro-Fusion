# アプリの配布と自動更新

Windowsの配布版は起動30秒後と1時間ごとにGitHub Releasesの新版を確認する。設定の「アプリの更新」からも確認できる。新版は自動ダウンロードし、通常のアプリ終了時にインストールする。タイマーを止める強制再起動は行わない。

「更新の準備ができました」と表示されたら、タイマーの区切りで設定の「再起動して更新」を押す。通常の終了時に適用し、自分で開き直すこともできる。更新に失敗した場合は設定に失敗を表示し、「更新を確認」で再試行できる。通信できなくても現在のアプリは使える。確認・取得に失敗した新版を適用しない。

設定の「再起動して更新」を押すと、取得済みの新版をサイレント適用し、完了後にアプリを自動で開き直す。ボタンはダウンロード完了後だけ表示し、タイマー動作中は無効にする。メインプロセスでも取得完了・計測停止を確認し、多重実行を防ぐ。一時停止中のタイマーは再起動するとリセットされるため、操作の近くに説明する。適用開始に失敗した場合は更新失敗を表示し、「更新を確認」で取得済みファイルを再確認してからやり直せる。通常の終了時適用も引き続き利用できる。

更新失敗の詳細はElectronのuserDataフォルダ内の `updates.log` に記録する。通常は `%APPDATA%/Yield/updates.log`。利用者向け画面には再試行方法を表示し、接続先の生の例外はログで確認する。

## masterから配布まで

1. masterへpushするとCIが型チェック・単体/結合テスト・本番ビルド・E2Eを実行する。
2. CI成功を受けてReleaseワークフローが、そのCIで確認したコミットをチェックアウトする。PRのCI、失敗したCI、既に公開したコミット、より新しいmasterに置き換わったコミットは公開しない。
3. package.jsonのバージョン、過去の安定版タグ、下書きを含むReleaseの番号を比較し、最大番号のパッチを1つ上げる。package.jsonとpackage-lock.jsonはビルド作業領域だけで更新する。masterにバージョン更新コミットを自動pushしないため、公開処理が再帰的に動くことはない。
4. Windows NSISインストーラ・blockmap・latest.ymlを作る。`npm run release:verify` で実ファイル名・サイズ・SHA・バージョンの一致とblockmapの存在を確認する。3つが揃ってからReleaseの下書きを作成・アップロードし、正式公開してLatestにする。ビルド中にmasterが進んだ場合は下書きのままにする。
5. 起動中のアプリが次の確認で取得する。pushした瞬間の即時更新ではなく、CI・配布ビルド・アプリの確認・終了を経て反映される。

ワークフローはリポジトリのGITHUB_TOKENを使う。利用者のPCにGitHubのトークンを配らない。配布先は公開リポジトリ `DoFer0910/Pomodoro-Fusion`。今後はvタグを手動pushする必要はない。大きなバージョン変更が必要な場合はpackage.jsonの番号を更新してPRでマージする。Releaseはその番号以上の未使用番号を採番する。

失敗したReleaseの再実行は新しい番号を使う。不要な下書きは管理者が確認して整理する。CIに成功したコミットが既に公開されている場合は再実行しても二重公開しない。

## 初回の導入とデータ

自動更新処理のない旧版は新版を自力で取得できない。初回のみGitHub Releasesの最新インストーラを起動して、既存と同じインストール先へ上書きする。既存の版が無料版・Pro版・本人用DevPro版のどれかを確認し、同じ版のインストーラを選ぶ。

更新処理はelectron-storeを読み書きせず、勤務記録・セッション・設定・ライセンス鍵を変更しない。appIdとproductNameも変更しない。初回の入れ替え前には設定のJSONバックアップを取っておくと、ユーザー側でもデータの確認ができる。

## 無料版・Pro版・開発起動

無料配布版のpackage.jsonは `yieldUpdateEdition: free`。Proの署名検証実装は従来どおりprivate側に置く。無料版の配布パイプラインへPro・DevProの実装を注入しない。

yield-proの `build:pro` は `yieldUpdateEdition: pro` を配布物に設定する。販売開始時にはProインストーラ・blockmap・latest.ymlを置く**Pro専用の公開配布リポジトリ**を用意し、`YIELD_PRO_UPDATE_REPOSITORY=owner/repo` を指定してビルドする。build.publishとアプリの更新先メタデータは同じ指定から作る。専用の更新先がないPro版は設定に未設定を表示し、無料版への更新を行わない。Pro版の自動ビルド・公開パイプラインはprivate側で管理する。

本人用 `build:dev-pro` は `yieldUpdateEdition: dev-pro`、`yieldUpdatePrivate: true`、privateの更新先を配布物へ設定する。既定の更新先は `DoFer0910/yield-pro`。誰でもProになる本人用インストーラを公開Releaseに載せない。開発起動、未パッケージのElectron、Windows以外は更新しない。

## 本人用Proの非公開更新

本人用ProのPCではGitHub CLI（gh）がインストールされ、`gh auth login` でprivateのyield-proへアクセスできる本人のアカウントにログインしていることが必要。公開版の利用者へGitHubログインを要求するものではない。

1. 本人用アプリが公開リポジトリの最新安定版とprivateの本人用Releaseを確認する。
2. 公開版の方が新しい場合、PCの既存のgh認証でprivateの `dev-pro-release.yml` を実行する。同じ版の進行中ビルドがあれば依頼を重ねない。追加の共有トークンやActions secretは用意しない。
3. privateのワークフローは非公開リポジトリであることと、入力が公開済みの最新安定版タグであることを確認する。そのタグの本体を取得し、CI後に本人用Pro実装へ差し替え、更新メタデータと一緒にprivateのReleaseへ載せる。失敗した下書きは再実行で完成させ、公開済みの同版は上書きしない。
4. アプリは「本人用Proの新版を準備中」と表示し、5分ごとに完成を確認する。完成するとPCのgh認証を使ってprivateのメタデータ・インストーラを取得し、通常のアプリ終了時に適用する。

認証情報を取得するのはElectronのメインプロセスだけで、更新通信中のメモリに保持する。レンダラー・ストレージ・配布物・リポジトリ・Actions secretへ書かない。ghの例外に含まれるstdoutはログへ渡さず、更新ログでもGitHub認証情報を伏せる。未ログイン、権限不足、ビルドや取得の失敗は設定画面で再試行できる。

PCの既存CLIログインからworkflow実行を依頼するため、本人のアカウントにはprivate側のActionsを実行できる権限が必要。本人用はアプリが起動しているとき、または次の起動後にビルドを依頼する。無料配布版はPCの稼働に関係なくmasterのCI後に作成される。

初回は両PRを反映し、publicの最初の安定版ができてから `gh workflow run dev-pro-release.yml --repo DoFer0910/yield-pro -f public_tag=vX.Y.Z` で本人用Releaseを一度作る。そのprivate Releaseの本人用インストーラで現在と同じ場所へ上書きする。以後の更新依頼・取得はアプリが行う。

## 検証の範囲

単体テストで起動・定期確認、並行実行の抑止、確認とダウンロードの例外、配布版の判定、バージョン採番を検証する。

手動更新操作のE2Eシェルでは起動時・定期の自動確認を停止し、手動の失敗・再試行の途中へ30秒の起動確認が割り込まないようにする。実アプリでは自動確認を停止しない。自動確認と手動操作の責務を分けるため、スケジュールは時間制御した単体テストで保証する。Electronの画面URL・読み込みと、GitHub確認の状態更新が完了してから表示を検証し、CIの速度による途中状態を成功・失敗として扱わない。

E2Eでは実際のElectron・preload・IPC・electron-updaterを使い、ローカルHTTP配布先から更新メタデータと検証用ファイルを取得する。503からの再試行、SHA不一致の拒否、正しいファイルのダウンロード、タイマー継続、保存データの保持を確認する。外部APIの単純なモックではなく、実際の更新ライブラリのHTTP・SHA検証経路を通す。PrismではNSISダウンロードとハッシュ検証を代替できないため、ローカルファイル配信を使う。

本人用フローはPrismのOpenAPI契約と実gh CLIで、公開リポジトリの拒否・ビルド依頼・重複抑止・完成待ちを検証する。実electron-updaterのPrivateGitHubProviderで認証付きメタデータ・インストーラ取得とSHA検証を通し、保存した鍵が変わらないことを確認する。テストでは実際のGitHub認証を使わず、ダミー認証とローカル配信だけを使う。

テスト環境でインストーラを実行しないよう、テスト専用のシェルだけ終了時適用を止める。再起動ボタンのE2Eは実NSIS updaterのquitAndInstallを通し、インストーラ起動部分だけをテスト専用のElectron再起動へ差し替える。サイレント適用・適用後自動起動の指定、計測中の拒否、適用開始失敗からの再試行、別プロセスの起動と保存データ保持を確認する。実インストーラの生成・同梱更新設定を別途確認し、GitHubでの正式公開とインストール済み版への適用は初回導入で確認する。
